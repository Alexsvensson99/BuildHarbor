# Security policy

BuildHarbor is a local command runner with a narrow storage guard. It is designed to stop a supported Xcode action before it writes managed output when the configured external volume or inspected project state cannot be verified. It is not a filesystem sandbox, an access-control boundary, or protection from a malicious project.

## Supported versions

Security fixes are provided for the latest 0.3.x release line. Version 0.1.x is no longer current.

Version 0.3.0 includes the guarded workspace, archive, export, and storage-reporting boundaries described below. The [0.3 verification record](docs/verification-0.3.md) separates controlled local evidence from CI and publication state.

## Reporting a vulnerability

Use [GitHub private vulnerability reporting](https://github.com/Alexsvensson99/BuildHarbor/security/advisories/new) for this repository. Include the affected version, a minimal reproduction, expected and observed behavior, and the security impact. Redact usernames, real volume UUIDs, signing material, access tokens, and private project paths.

If private reporting is unavailable, open a public issue that asks for a private reporting channel without including vulnerability details, logs, or reproduction steps. Please do not test a report against data, machines, or accounts you do not own or have permission to use.

## Threat model

BuildHarbor assumes one trusted local user controls the project configuration, local configuration, source checkout, external volume, and command being run. Project build phases and tools execute with that user's normal authority. Configuration from an untrusted checkout is therefore code-adjacent input and must be reviewed before `run`.

The 0.1 security boundary covers:

- confusing an internal directory, another mounted volume, or a replaced mount with the approved external volume;
- a mismatched volume UUID, non-APFS filesystem, or non-external device;
- output paths that escape the approved storage root;
- existing symlinks or filesystem objects that conflict with the plan;
- two BuildHarbor runs for the same project racing each other;
- a caller supplying managed output flags, managed build settings, or `-xcconfig` to override routing;
- losing the outcome when a build fails or receives a signal.

Version 0.3.0 adds:

- bounded static traversal of a selected project or workspace, every referenced project, shared scheme metadata, xcconfig source, package references, phases, rules, and relevant output settings;
- rejection of private or autogenerated schemes, script phases, custom rules, unsupported graph objects, unsafe copy destinations, unresolved references, and source-defined managed output overrides;
- rejection of shared schemes that select test plans through `TestPlans` or `TestPlanReference`, and caller-supplied `-testPlan`, because BuildHarbor does not inspect test-plan contents;
- a guarded selected-scheme/action effective-setting query, plus `-alltargets` queries for every statically discovered member project;
- rejection of unknown projects or targets, missing member targets, conflicting duplicate settings records, unresolved output paths, and output paths outside the approved storage root;
- archive signing limits: one simple macOS application, with signing disabled or manual ad-hoc identity `-`, and no team, provisioning profile, keychain, extra signing flags, or private identity;
- export binding to a successful BuildHarbor archive receipt, exact project/storage/Xcode identity, and an unchanged archive digest; and
- rejection of export inputs containing symlinks, multiply linked regular files, special files, or more than one application.

The effective-setting payload is held in bounded memory and is not written to the receipt. The receipt records only a validation summary. The portable configuration and receipt objects retain `schema_version: 1`; the newer receipt fields are additive.

The archive guard validates effective signing settings and structurally inspects the archive and application. It does not invoke `codesign` to audit the produced signature or team identifier. Strict ad-hoc/no-team verification belongs to the controlled fixture evidence, not the runtime security boundary.

Version 0.3.0 also adds a separate read-only operation:

- every supplied project configuration must identify one exact common mount, volume UUID, and storage root;
- the volume must still be mounted, unlocked, external, APFS, UUID-matched, and readable/traversable, while a read-only volume or capacity below the build threshold is acceptable for reporting;
- the scanner opens directories and regular files with read-only, no-follow flags, reads inode metadata, and never reads file contents or creates, updates, removes, or renames managed files;
- symlinks are never followed, special files are not opened, and both are reported only as ignored-entry counts;
- unique regular-file inodes are classified as one known project, shared by multiple known projects, or unattributed; unknown locations, ambiguous project IDs, incomplete hard-link observations, and conflicting inode metadata remain unattributed; and
- a permission error, mutation, filesystem boundary, volume/root identity change, or fixed scan limit produces an incomplete report with stable issue codes and observed lower bounds rather than a misleading zero or success result.

Reporting includes `tool_version` and schema version 1, but does not include scanned file names. A complete report exits 0; an incomplete report exits 2. A safely verified volume whose configured storage root is absent produces a complete empty report.

`run` must revalidate the mounted APFS external volume and UUID before creating output directories and again at the execution boundary defined by the implementation. It must fail closed, hold an advisory lock for the project, and forward termination signals. After storage preparation and child execution it makes a best-effort receipt write. A guard failure before verified storage exists is reported on stderr because writing a receipt would violate the guard. `doctor` and `plan` are read-only; `doctor` does not inspect project input, and `plan` reads static Xcode application metadata without executing `xcodebuild`.

## Known residual risks

There is an unavoidable time-of-check/time-of-use window between volume validation and later filesystem writes by Xcode and its children. The volume can be disconnected, remounted, or fail during a build. BuildHarbor can detect the condition at its own checkpoints and report an incomplete or failed run, but it cannot make a mid-build disconnection atomic or guarantee the state of partially written build products.

Signals can also race with process creation and with grandchildren started by project scripts. BuildHarbor forwards supported signals and records what it observes, but a project process that daemonizes or ignores signals may outlive the direct child.

The storage guard controls the paths BuildHarbor manages. A compiler, dependency, Xcode service, package tool, or other process can still read or write elsewhere with the user's permissions. Version 0.3.0 rejects project script phases and custom rules, but that does not turn Xcode into a sandbox. Receipts and logs may contain local paths, configured project IDs, bundle identifiers, archive identities, and project metadata. Storage reports also include configured project IDs. Treat those IDs as potentially sensitive and redact them before sharing when they identify private work.

Advisory file locks coordinate cooperating BuildHarbor processes only. Other tools, GUI Xcode, and direct `xcodebuild` invocations do not honor those locks.

Storage reporting is best-effort and non-atomic. Files can appear, disappear, change, or gain links while the scan runs. The scanner rechecks files, root identity, and volume identity where its contract defines checkpoints, then marks observed failures incomplete. It does not freeze the filesystem or produce a transactionally consistent snapshot.

The reporting deadline is cooperative. It is checked between filesystem calls and cannot cancel a kernel call that is already blocked. Opening a file or directory for metadata can also allow the operating system to update access time. BuildHarbor does not write contents or metadata intentionally and makes no access-time guarantee.

## Out of scope

BuildHarbor does not claim to secure a hostile multi-user machine, isolate untrusted build code, police every file opened by Xcode, manage signing credentials, migrate or delete existing data, change global Xcode settings, or monitor builds as a background service. Version 0.3.0 accepts only statically traversable project/workspace graphs and shared schemes, and blocks any graph shape it cannot account for before execution. It rejects test plans rather than claiming to inspect them. Archive/export support does not cover Developer ID, App Store, notarization, provisioning, installer packages, iOS-family platforms, or caller-supplied export options. The storage report does not calculate physical disk use, APFS clone sharing, snapshots, purgeable space, or reclaimable capacity and does not offer cleanup.
