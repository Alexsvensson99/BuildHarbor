# ADR 0002: Inspect effective settings before local archive and export

- Status: Accepted for 0.2 development; controlled local integration passed, release gate pending
- Date: 2026-10-04
- Applies to: BuildHarbor 0.2 development line

## Context

The 0.1 storage guard owns the command-line routes it adds, but a real Xcode graph can change output paths through projects, targets, configurations, xcconfig files, workspaces, and nested project references. A single selected-scheme settings query is also incomplete: it does not prove that every statically referenced project and target uses the managed storage root.

Archive and export add a second boundary. Xcode's archive action expects action-specific packaging directories, and forcing ordinary `SYMROOT`, `OBJROOT`, and `DSTROOT` values onto the main archive command can break that layout. Export can invoke signing and distribution behavior that needs identities, profiles, keychains, accounts, or user interaction. BuildHarbor must not discover or use those credentials during unattended local work.

Version 0.2 therefore supports a small, fail-closed surface rather than general Xcode archive and distribution automation. It retains the exact Xcode 27.0 (27A266a) allowlist. One controlled local build/test/workspace/archive/export sequence has passed on that toolchain, including strict verification of an ad-hoc exported application with no team identifier. A separate remote-package regression passed build, repeat build, and test while exercising the routed repository cache and selected compiler-artifact reuse. The 94-test unit/process suite has passed under Python 3.11.13 and 3.13.4. New-release CI and review remain open; this decision is not a broader compatibility claim or a published-release announcement.

## Decision

### Planning stays static and read-only

For build, test, and archive, `plan` reads the selected `.xcodeproj` or `.xcworkspace` and traverses every referenced project within the policy root. It parses shared schemes, project objects, target/configuration data, xcconfig source, package references, phases, rules, copy destinations, and the managed settings set with explicit size, count, and depth limits. Export planning instead reads and fingerprints the managed archive and its receipt.

Planning never starts `xcodebuild`, resolves packages, creates result bundles, takes a lock, or writes to the filesystem. It identifies Xcode by reading the selected application's version metadata. Private and autogenerated schemes are unsupported because they are not part of the inspected shared source graph.

The static inspector rejects anything it cannot safely account for, including unresolved or escaping references, symlinks in inspected source paths, unknown object types, script phases, custom build rules, legacy targets, unsupported synchronized groups, unsafe copy destinations, unsupported package forms, and source-defined managed output settings. This can reject a valid Xcode project. That false block is preferable to claiming that an uninspected member or executable phase is safe.

### Guarded execution inspects effective settings

After volume validation, directory preparation, and acquisition of the per-project lock, `run` starts bounded Xcode metadata queries before the requested action:

1. One `-showBuildSettings -json` query uses the selected shared scheme, requested action, selectors, and managed routes. It uses the same Derived Data, package, compiler-cache, temporary, and output controls as the requested action, with a separate unique result bundle.
2. When a workspace or nested graph contains more than one project, one `-project ... -alltargets` query runs for every statically discovered project. All member queries use the explicit configuration and SDK supplied by the caller and the accepted architecture, job, switch, and boolean selections where relevant.
3. The member queries deliberately omit `-derivedDataPath`; that flag/action combination is not supported by the tested Xcode command surface. They receive explicit managed build roots, package paths, compiler/cache settings, `TMPDIR`, and unique result bundles instead.
4. Xcode 27 can return byte-for-byte identical records twice from an `-alltargets` member query. BuildHarbor ignores only an exact repeated record for the same member target. Conflicting duplicates, selected-scheme duplicates, unknown projects or targets, and incomplete target sets remain errors.

Each query has a time and output-size limit, receives no stdin, discards stderr, forwards supported termination signals, and is reaped before the lock is released. Captured settings remain in memory. Receipts contain counts and status, never the full settings object or inherited environment.

BuildHarbor checks the resolved directory and file output-setting set, including dynamic `OBJECT_FILE_DIR_*` and link-file-list settings. Required roots and product-relative values must be resolved, free of control or bidirectional-formatting characters, and contained by the verified storage root. It reports a setting and bounded safe value when useful, but does not invent a definition source when Xcode's JSON does not expose one.

The source graph, volume, package manifests where applicable, selected Xcode, and unique output leaves are checked again after metadata inspection. A query failure or changed input blocks the main action.

### Archives are local, simple, and non-credentialed

The `archive` action is limited to one macOS application. Its effective settings must show either disabled code signing or manual ad-hoc signing with `CODE_SIGN_IDENTITY=-`. BuildHarbor rejects another platform, expanded certificate identity, signing team, provisioning profile, signing keychain, extra signing flags, and Swift runtime signing overrides.

The main archive command uses managed `-derivedDataPath` and `-archivePath`. It does not inject the ordinary build `SYMROOT`, `OBJROOT`, or `DSTROOT` values. Xcode derives the archive packaging roots below:

```text
DerivedData/Build/Intermediates.noindex/ArchiveIntermediates/<scheme>/
```

BuildHarbor predicts those action-specific product, intermediate, and installation roots in the plan, then requires the effective archive settings to resolve beneath the managed external Derived Data tree before starting the archive. This decision does not claim that generic build-root injection works for archive packaging.

A zero Xcode exit status is not enough. The produced archive must have readable archive/application property lists, identify exactly one `Products/Applications/*.app`, contain a non-empty regular executable, and agree on its bundle identifier. The successful receipt stores a bounded archive digest and the inspected application identity.

### Export is a receipt-bound local copy

The only accepted export form is:

```text
-exportArchive -archivePath ARCHIVE
```

The archive must be inside the configured project's managed `Archives` directory and have a successful schema-1 BuildHarbor archive receipt for the same run ID, project ID, source identity, storage layout, and exact Xcode build. Its current digest and application identity must match the receipt.

The archive walk is bounded by entries, bytes, and time. It rejects symlinks, special files, cross-filesystem entries, changing files/directories, and regular files with multiple hard links. These restrictions prevent export from following or silently sharing uninspected archive content.

BuildHarbor creates a unique export-options file with the fixed values below and passes a unique managed export directory to Xcode:

```plist
method = mac-application
destination = export
```

Callers cannot supply an export path, export-options plist, signing method, or signing credentials. BuildHarbor rechecks the archive and receipt before writing the options file and before launching export. A successful export must contain an application property list.

### Existing schema numbers remain stable

Portable and local configuration stay at `schema_version = 1`. Receipts also stay at schema 1. Version 0.2 adds project/source identity, settings-validation summary, input identity, archive digest, and archived-application fields without changing existing field meanings. Consumers must continue to ignore unknown additive fields.

## Evidence boundary

The installed `xcodebuild -help` for Xcode 27.0 (27A266a) documents `-showBuildSettings`, `-json`, `-alltargets`, `-archivePath`, `-exportArchive`, `-exportPath`, and `-exportOptionsPlist`. Apple's [Build settings reference](https://developer.apple.com/documentation/xcode/build-settings-reference) defines the output settings checked here, and [Configuring the build settings of a target](https://developer.apple.com/documentation/xcode/configuring-the-build-settings-of-a-target/) describes command-line setting precedence.

Those interfaces establish the command surface, not BuildHarbor compatibility. The controlled local fixture has completed build, test, a two-member workspace build, archive, and export on the exact allowlisted Xcode, and the exported app passed `codesign --verify --strict` with an ad-hoc signature and no team identifier. The GUI was not launched. The [0.2 verification record](../verification-0.2.md) carries the exact environment, separate remote-package regression, corrected-baseline history, and remaining limits. Complete new-release CI and review still have to pass before a 0.2 release claim.

## Alternatives considered

### Run settings inspection during `plan`

This would make the preview depend on Xcode execution and package/build-system metadata behavior. It would break the read-only planning contract. Static analysis belongs in `plan`; executable effective-setting checks belong inside the guarded, locked `run` path.

### Trust only the selected scheme query

A workspace scheme can omit or conditionally reach project targets that still belong to the static graph. Querying each statically discovered project provides a second completeness check and lets BuildHarbor reject disagreement between source metadata and Xcode's effective view.

### Allow scripts and inspect their declared outputs

Declared output lists do not constrain what a script can do with the local user's authority. Version 0.2 rejects executable project phases and custom rules instead of treating declarations as a sandbox.

### Pass ordinary build roots to archive

The tested archive packaging flow depends on Xcode's `ArchiveIntermediates` layout below Derived Data. Forcing ordinary roots can produce a broken archive. BuildHarbor lets Xcode derive that layout and validates the resolved paths before execution.

### Accept caller-supplied export options

That would open signing, distribution, upload, account, and provisioning surfaces that are outside unattended local storage routing. The fixed local Copy App plist is intentionally much narrower.

## Consequences

The 0.2 development surface can account for workspace and nested-project output settings without weakening the read-only plan contract. Archives and exports remain local and do not require private signing material. Receipts can bind an export to the exact successful archive that BuildHarbor inspected.

The cost is compatibility. Many ordinary projects use scripts, custom rules, private schemes, complex package graphs, multiple products, real signing, or distribution exports and will be rejected. Effective-setting queries are Xcode processes and can still touch toolchain-managed metadata outside BuildHarbor's routes. The volume can disconnect after a check, Xcode can spawn behavior BuildHarbor does not control, and this design remains a trusted-local-user storage guard rather than a filesystem sandbox.
