# How BuildHarbor differs from adjacent tools

This comparison is based on the projects' own documentation and source as reviewed on 2026-10-03. It describes different jobs, not a winner. “Not documented” means the cited primary source does not make that claim; it is not proof that a feature can never be configured.

BuildHarbor 0.1.0 has one narrow job: before an explicit command-line build or test for one plain `.xcodeproj`, verify one configured external APFS volume by mount, external-device status, and UUID; then route managed per-project output paths beneath its storage root. Workspaces and nested project references are rejected. `doctor` and `plan` are read-only. `run` fails closed, uses a per-project lock, forwards signals, and attempts a receipt after the child exits while the destination remains verified. Earlier failures use stderr and the process exit status. The initial allowlist accepts exactly Xcode 27.0 (27A266a). Guarded build and test fixtures, including an HTTP Git dependency that populated the routed checkout and repository cache, passed on Apple Silicon with macOS 27.0 (26A428). [The verification record](verification.md) does not extend that evidence to other systems or to global manifest and package metadata caches.

| Tool | Primary job in its own documentation | Storage behavior | Execution and safety boundary |
| --- | --- | --- | --- |
| BuildHarbor 0.1.0 | Guard and run explicit command-line Apple builds/tests for one plain `.xcodeproj` | Per-project paths on one UUID-pinned external APFS volume; no migration or cleanup | Rejects workspaces/nested projects and blocks on volume/path conflicts; no GUI Xcode, archive/export, global settings, background service, or filesystem-sandbox claim |
| [DevCleaner (`vashpan/xcode-dev-cleaner`)](https://github.com/vashpan/xcode-dev-cleaner#readme) | Inspect and delete categories of Xcode-generated data in a macOS GUI | Cleans Device Support, Archives, Derived Data, documentation caches, and old simulator/device logs | Its README warns that it relies on Xcode's internal folder structure and undocumented behavior; it does not document external-volume routing or build execution |
| [mac-ssd-rescue](https://github.com/Viniciuscarvalho/mac-ssd-rescue#readme) | Migrate fixed global Xcode, simulator, and SwiftPM directories to external storage and replace them with symlinks | Uses `rsync`, removes the original after its verification step, creates global symlinks, and provides restore/status/usage commands | Its [script](https://github.com/Viniciuscarvalho/mac-ssd-rescue/blob/main/mac-ssd-rescue.sh) compares file counts, enumerates `/Volumes`, and does not implement a volume-UUID check; it is migration rather than per-run project routing |
| [VibeChard](https://github.com/Maples7/VibeChard#readme) | Isolate parallel Apple-development agents with a worktree, branch, build paths, and simulator clone per task | Keeps per-task Derived Data, module cache, SwiftPM data, and results under its task layout | Its Xcode shim injects isolation flags and its lifecycle guards dirty worktrees; the cited docs do not describe pinning those paths to a particular external-volume identity |
| [fastlane](https://docs.fastlane.tools/) | Automate Apple build, test, signing, archive, export, and delivery workflows | `scan` and `gym` expose Derived Data, result-bundle, build, archive, and output path parameters | [`scan`](https://docs.fastlane.tools/actions/scan/) and [`gym`](https://docs.fastlane.tools/actions/gym/) wrap `xcodebuild`; their cited docs do not claim external-volume identity validation |

## Practical boundaries

DevCleaner addresses reclaiming space through deletion. mac-ssd-rescue addresses moving existing global data and making Xcode follow symlinks. VibeChard addresses collisions between concurrent agent tasks. fastlane addresses repeatable build, test, signing, and delivery automation. BuildHarbor 0.1 addresses destination identity before a narrow build or test begins.

Those scopes can overlap at the filesystem or command line. BuildHarbor has not verified compatibility with these tools, so it should not be described as a drop-in companion or replacement. A wrapper that adds its own `xcodebuild` output flags, an existing global symlink, or a tool-managed worktree path may conflict with BuildHarbor's allowlist and guard. That interaction needs a concrete fixture before any compatibility claim.

## Source notes

- DevCleaner's README documents macOS 14.x and Xcode 15.x testing and warns about reliance on undocumented Xcode behavior. Its [2.8.0 release](https://github.com/vashpan/xcode-dev-cleaner/releases/tag/2.8.0) was published on 2025-11-11. This comparison does not infer newer-Xcode compatibility.
- mac-ssd-rescue's README describes its claimed platform/filesystem requirements and migration workflow. The source is the basis for the narrower observations about file-count verification, mount enumeration, and the absence of a UUID check.
- VibeChard's README documents its worktree/task model, isolated paths, shim, simulator cloning, lifecycle commands, and stated platform limits. Its [v1.2.2 release](https://github.com/Maples7/VibeChard/releases/tag/v1.2.2) was published on 2026-09-23.
- fastlane's official action documentation supports the build/test/archive/output-path statements. It does not make BuildHarbor's volume-guard claim.
- Apple's [build settings reference](https://developer.apple.com/documentation/xcode/build-settings-reference) and [build-setting precedence documentation](https://developer.apple.com/documentation/xcode/configuring-the-build-settings-of-a-target/) support BuildHarbor's routing rationale, but neither source proves complete write isolation.
