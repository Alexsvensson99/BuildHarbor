# BuildHarbor 0.3.0

Version 0.3.0 is the first release after 0.1.0. It includes the workspace, effective-setting, archive, and export work developed during the unpublished 0.2 checkpoint, plus read-only managed-storage reporting.

## What changed

- `plan` can statically inspect bounded project and workspace graphs with shared schemes and nested project references while remaining read-only.
- `run` checks the selected scheme/action settings and every statically discovered member project before build, test, or archive begins.
- `archive` supports one simple macOS application with signing disabled or manual ad-hoc identity `-`.
- `-exportArchive` performs a local Copy App export from a successful, unchanged BuildHarbor-managed archive using generated fixed options and a unique destination.
- `report [--project-dir DIR ...] [--json]` accounts for regular-file storage as project, shared, or unattributed without requiring Xcode or changing managed data.
- Configuration and receipt `schema_version` remain 1. New receipt and report fields are additive.

## Install

Install the tagged source in a virtual environment:

```sh
git clone --branch v0.3.0 --depth 1 https://github.com/Alexsvensson99/BuildHarbor.git
cd BuildHarbor
python3 -m venv .venv
.venv/bin/python -m pip install .
.venv/bin/buildharbor --version
```

BuildHarbor is distributed through GitHub. Version 0.3.0 is not published to PyPI, Homebrew, or another package registry.

## Compatibility

- Python 3.11 or newer; the runtime uses only the standard library.
- Build, test, archive, and export are allowlisted only for Xcode 27.0, build 27A266a.
- Controlled integration ran on Apple Silicon with macOS 27.0 (26A428).
- `report` does not require Xcode, but it still requires the configured external APFS volume, UUID, and storage root to be verified.

No adjacent Xcode release, another host architecture, another project shape, private signing identity, or distribution workflow is implied.

## Verification

- All 117 unit and small-process tests passed under Python 3.11.13 and 3.13.4.
- Controlled fixtures passed build, repeat build, test, a two-member workspace build, archive, local export, and remote-package repository-cache routing.
- The exported fixture passed strict `codesign` verification with an ad-hoc signature and no team identifier. BuildHarbor's runtime does not itself run that signature audit.
- A real-storage report fixture reconciled project, shared, and unattributed data, plus absent-root and incomplete lower-bound cases, while preserving the checked content and metadata.
- An isolated installation of the committed candidate revision passed before release preparation. This is not a fresh installation from the final tag.
- Publication requires both GitHub Actions matrix jobs to pass for the exact release commit; the GitHub Release records the verified run link.

The [0.3 verification record](https://github.com/Alexsvensson99/BuildHarbor/blob/v0.3.0/docs/verification-0.3.md) gives commands, evidence identifiers, exact counts, and the boundary between local, CI, and publication evidence.

## Remaining limits

- BuildHarbor is a trusted-local-user storage guard, not a filesystem sandbox. Xcode and its children can still access locations outside managed routes with the user's authority.
- Script phases, custom build rules, private or autogenerated schemes, unsupported graph objects, unsafe copy phases, shared schemes that select test plans through `TestPlans` or `TestPlanReference`, and caller-supplied `-testPlan` are rejected.
- Archive and export do not support Developer ID, App Store, notarization, provisioning, installer packages, iOS-family platforms, signing credentials, or caller-supplied export options.
- Some SwiftPM manifest and metadata caches and other toolchain-managed state remain outside the supported repository-cache routing claim.
- Storage reports are non-atomic. Logical bytes and allocated blocks do not measure APFS physical use, clone sharing, snapshots, purgeable space, or reclaimable capacity. Incomplete scans report observed lower bounds.
- Reports contain configured project IDs. Treat them as potentially sensitive and redact them before sharing when they identify private work.
- There is no GUI Xcode control, cleanup, migration, global Xcode configuration, simulator relocation, background service, registry publication, or external developer validation.
